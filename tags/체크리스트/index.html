AI/ML 트렌드: 'FaceHugger' 취약점이 보여준 trust_remote_code의 함정

2026년 8월 3일, The Hacker News가 Hugging Face의 이미지·영상 생성 라이브러리 Diffusers에서 ‘FaceHugger’라는 이름이 붙은 취약점 3건(CVE-2026-44827, CVE-2026-45804, CVE-2026-44513)을 보도했습니다. 세 취약점의 공통점은 trust_remote_code 옵션을 우회해, 사용자가 명시적으로 신뢰하지 않은 원격 코드를 로딩 시점에 실행시킬 수 있다는 점입니다. 겉으로는 평범한 모델/파이프라인 로딩 API처럼 보이는 지점에서 임의 코드 실행(RCE)까지 이어질 수 있다는 게 핵심 위험입니다. trust_remote_code는 Hugging Face 생태계에서 커스텀 모델 클래스나 파이프라인 코드를 저장소에서 그대로 내려받아 실행하도록 허용하는 플래그입니다. 원래 의도는 분명합니다 — 표준 아키텍처에 없는 실험적 모델도 빠르게 써볼 수 있게 하는 편의 기능이죠. 하지만 이 옵션은 태생적으로 “이 코드를 믿습니까?“라는 질문을 사용자에게 떠넘기는 구조입니다. FaceHugger는 바로 그 신뢰 경계를 실제로는 지켜지지 않게 만드는 우회 경로였습니다. 즉 사용자가 trust_remote_code=False로 안전하다고 믿고 있어도, 특정 로딩 경로에서는 검증 없이 원격 코드가 실행될 수 있었다는 뜻입니다. ...

Hermes/리오 팁: '신뢰 플래그'는 보안 경계가 아니라 정책 선언일 뿐입니다

Hugging Face Diffusers의 ‘FaceHugger’ 취약점은 trust_remote_code=False처럼 “신뢰하지 않겠다"고 선언한 옵션이 실제로는 지켜지지 않을 수 있다는 걸 보여줬습니다. Hermes/리오처럼 여러 스킬·플러그인·크론 작업이 자동으로 외부 코드나 데이터를 호출하는 환경에서는 같은 함정이 그대로 재현될 수 있습니다. “이 도구는 안 쓰기로 했다”, “이 자격증명은 이 범위 밖에서 안 쓴다"는 선언이 실제 실행 경로에서도 지켜지는지는 별개의 문제입니다. 이번 사건에서 얻을 수 있는 실전 원칙은 세 가지입니다. 1. 정책 선언과 실행 검증을 분리해서 확인하기 Hermes 설정에서 “이 플러그인은 비활성화했다”, “이 자격증명은 특정 권한만 가진다"고 적어두는 것과, 실제로 그 경계가 실행 시점에 강제되는지는 다릅니다. 예를 들어 Gemini Enterprise 연동에서 서비스 계정 JSON을 받았을 때 testIamPermissions로 실제 권한을 검증했던 것처럼, 자동화에 새 자격증명이나 코드 실행 경로를 추가할 때마다 “선언된 권한"이 아니라 “실제로 허용되는 동작"을 별도 호출로 확인하는 습관이 필요합니다. ...
