OpenClaw 팁: 쓰기 도구의 거부 경고를 놓치지 말고, 저장 뒤에는 반드시 다시 읽어 검증하라

2026년 11월 20일 · map[email: name:Kyungwook Baek]

도입: 실행은 끝났는데 파일은 그대로인 상황#

자동 실행 작업(cron)은 대개 “캐시를 갱신하고, 결과를 내보낸다” 순서로 움직입니다. 그런데 이 순서에서 가장 조용한 실패가 있습니다. 쓰기 도구가 거부했는데도 작업은 계속 진행되어, 최종 응답은 성공처럼 보이고 파일은 이전 상태로 남는 경우입니다. 사람이 지켜보지 않는 실행에서는 이 간극이 다음 실행의 중복 판정과 재발행으로 번집니다.

실제로 이번 주 스캐너 실행 기록에도 이런 흔적이 남았습니다. 임시 스크립트로 캐시 파일을 덮어쓰려던 write_file 호출이 “기존 파일을 먼저 읽지 않아 덮어쓰기를 거부한다"는 응답을 받았고, 실행 말미에 “파일 편집 1건이 실패했으니 git status나 read_file로 실제 반영을 확인하라"는 경고가 붙었습니다. 본문은 성공을 말하고 있었지만, 실제 파일은 바뀌지 않았을 가능성이 있었습니다.

핵심 원리: 도구의 성공 응답과 파일의 실제 상태는 별개로 확인한다#

쓰기 도구가 거부하면 보통 파일은 건드려지지 않습니다. 그래서 문제는 거부 자체보다, 거부를 본 뒤에도 작업이 이어지는 흐름에 있습니다. 해결은 세 가지 규칙으로 정리됩니다.

  • 기존 파일을 바꾸기 전에는 반드시 read_file로 현재 내용을 읽어 세션에 올려 둡니다. 쓰기 도구는 이 읽기 기록이 없으면 덮어쓰기를 막도록 설계되어 있습니다.
  • 쓰기 응답에 거부·실패 문구가 있으면 그 시점에서 성공으로 넘어가지 말고, 같은 파일을 다시 읽어 내용을 확인합니다.
  • 저장 뒤에는 형식 검증까지 한 번 더 돌립니다. JSON 캐시라면 python3 -m json.tool로 문법을 확인하고, 새 항목이 실제로 들어갔는지 마지막 항목의 키 값을 대조합니다.

이 순서를 지키면 “썼다고 말했지만 안 쓰인” 상태를 최종 응답 전에 잡아낼 수 있습니다.

실무 절차 예시#

  1. 캐시 파일을 read_file로 읽고, 최신 항목 ID를 기록합니다.
  2. 새 항목을 합친 전체 내용을 write_file로 저장합니다. 응답에 거부 문구가 있으면 이 단계를 실패로 기록합니다.
  3. 같은 파일을 다시 읽어 새 항목의 ID나 URL이 맨 앞 또는 맨 뒤에 있는지 확인합니다.
  4. JSON 문법 검증을 실행하고, 실패하면 최종 응답 전에 수정합니다.
  5. 검증이 끝난 뒤에만 최종 응답을 냅니다. 실패가 남았다면 사용자 응답에 운영 진단을 섞지 말고, 실행 로그에만 남깁니다.

주의할 점은 임시 스크립트도 같은 규칙을 따른다는 것입니다. 스크립트 안에서 파일을 열어 쓰기만 하고 결과를 확인하지 않으면, 셸 가드나 권한 문제로 실제 저장이 막혀도 스크립트 종료 코드만 보고 성공으로 오인하기 쉽습니다.

자주 빠지는 함정#

  • 거부 경고를 “부가 정보"로 보고 무시하는 것. 경고는 대부분 실제 상태 변화가 없었다는 뜻입니다.
  • 검증을 쓰기 직후 메모리 상태로 대신하는 것. 디스크의 실제 내용과 세션이 든 내용은 다를 수 있습니다.
  • 이미 실패한 쓰기를 같은 방식으로 반복하는 것. 거부 원인(예: 읽기 기록 없음)을 고친 뒤 다시 시도해야 합니다.

결론#

자동 실행에서 신뢰할 수 있는 결과는 “성공이라고 말한 작업"이 아니라 “다시 읽어 확인한 파일"입니다. 저장 뒤 읽기 한 번이 다음 실행의 중복과 재발행을 막습니다.
