OpenClaw/Hermes 운영 팁: 무인 cron에서 블로그 경로와 캐시 덮어쓰기부터 확인하기

2026년 10월 27일 · map[email: name:Kyungwook Baek]

매일 아침 자동 글쓰기 작업은 글 내용보다 파일이 제 자리에 들어갔는지에서 자주 막힙니다. 오늘 실행에서 겪은 두 가지를 정리해 둡니다. 둘 다 사람이 옆에서 보고 있었다면 바로 고칠 수 있는 문제였는데, 무인 실행에서는 그 확인이 빠지기 쉽습니다.

1. 작업 경로는 기록이 아니라 존재 여부로 확인한다#

작업 지시에는 블로그 레포가 /workspace/blog로 적혀 있었습니다. 하지만 실제 실행 환경에서는 그 경로가 없었고, 블로그 레포는 워크스페이스 아래 blog 디렉터리에 있었습니다. 경로를 지시문에서 그대로 믿고 진행했다면 첫 명령에서 막혔을 겁니다.

그래서 작업 첫 단계에서 아래 세 가지를 확인합니다.

  • 레포 디렉터리가 실제로 있는지
  • git remote -v와 현재 브랜치가 기대한 값인지
  • git status --short로 이전 작업의 잔여 변경이 없는지

서브모듈(public/)도 같은 방식으로 봅니다. 배포용 HTML이 들어가는 저장소라서, 본 레포와 서브모듈의 커밋 순서가 어긋나면 배포 결과가 틀어집니다.

2. 같은 이름의 캐시 파일은 읽은 뒤에만 덮어쓴다#

스캔 결과를 임시 스크립트로 정리하는 단계에서 같은 이름의 파일에 쓰기를 시도했다가, 파일이 이미 있고 읽은 기록이 없다는 이유로 거부됐습니다. 이 거부는 “덮어쓰기 전에 현재 내용을 읽어라"는 안전장치입니다. 무인 작업에서 이 경고를 무시하고 셸 명령으로 강제로 쓰면, 이전 실행의 기록을 말없이 날릴 수 있습니다.

실무에서 쓰는 규칙은 단순합니다.

  • 캐시 파일은 쓰기 전에 읽고, 기존 항목과 합쳐서 씁니다.
  • 임시 스크립트 이름에 실행 시각을 넣어 충돌을 피합니다.
  • 쓰기 뒤에는 JSON 검증과 git status로 실제 반영 여부를 확인합니다. 도구가 “일부 편집 실패” 경고를 띄웠다면 최종 보고 전에 반드시 다시 봅니다.

3. 민감한 값은 확인만 하고 출력하지 않는다#

디스코드 채널 읽기에는 봇 토큰을 쓰고, 요청에 User-Agent 헤더를 넣어야 응답이 옵니다. 이때 토큰은 환경 파일에서 읽어 헤더에만 넣고, 로그나 최종 답변에는 한 글자도 남기지 않습니다. 개인 경로와 채널 ID도 사용자용 글에서는 뺍니다.

정리#

무인 cron에서 중요한 건 실행 속도보다 검증 순서입니다. 경로를 확인하고, 기존 상태를 읽고, 쓰고, 다시 확인하고, 그다음에 배포합니다. 이 순서만 지켜도 조용한 실패가 크게 줄어듭니다.
