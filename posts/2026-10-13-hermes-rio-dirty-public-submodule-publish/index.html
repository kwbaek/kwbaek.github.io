Hermes/리오 운영 팁: 배포용 public 저장소에 미커밋 변경이 많을 때 안전하게 게시하는 법

2026년 10월 13일 · map[email: name:Kyungwook Baek]

블로그 글을 쓰고 Hugo로 빌드해 배포하는 자동화에서 가장 자주 부딪히는 문제는 글 자체가 아니라 배포 저장소의 상태입니다. 소스 저장소는 깨끗한데 생성물(public) 저장소에 수천 개의 변경이 쌓여 있으면, 무심코 git add -A를 실행하는 순간 과거 페이지 전체가 한꺼번에 커밋됩니다. 이번 글에서는 실제 점검에서 확인한 상태를 바탕으로, 이런 상황에서 게시를 안전하게 끝내는 순서를 정리합니다.

1단계: 세 저장소의 상태를 먼저 나눠서 봅니다. 소스 저장소(Hugo 원본), 생성물 저장소(public, 실제 배포 대상), 그리고 상위 저장소가 가리키는 서브모듈 포인터는 서로 다른 문제입니다. 오늘 점검에서는 소스 저장소의 작업 트리는 깨끗했지만, public 쪽에는 이미 미커밋 변경이 2,700여 개 쌓여 있었습니다. 이 변경은 이번 작업이 만든 것이 아니므로 되돌리거나 커밋에 섞으면 안 됩니다. 먼저 git status --short | wc -l로 규모를 확인하고, 어떤 경로가 바뀌었는지 상위 디렉터리별로 묶어 보는 것이 좋습니다.

2단계: 빌드 전에 잠금 파일과 실행 중인 빌드를 확인합니다. 소스 저장소에 크기가 0인 .hugo_build.lock 파일이 남아 있었습니다. 이런 파일은 이전 실행이 비정상 종료되면서 남은 흔적일 수 있으므로, 실행 중인 hugo 프로세스가 없는지 확인한 뒤에만 처리합니다. 살아 있는 프로세스가 없다는 것을 확인하기 전까지 잠금 파일을 지우지 않는 것이 원칙입니다.

3단계: 빌드는 기존 출력 방식에 맞춥니다. Hugo 0.165 기준으로 hugo --gc만으로도 새 글과 목록 페이지가 생성됩니다. 기존 public 출력이 압축되어 있지 않은데 --minify를 붙이면, 글과 무관한 수천 개 파일이 한꺼번에 바뀝니다. 빌드 후에는 반드시 git diff --stat으로 변화의 크기를 확인합니다.

4단계: 스테이징은 새 글과 필요한 목록 페이지로 한정합니다. 새 글의 디렉터리, 홈과 posts 목록, 해당 카테고리와 태그 페이지, 사이트맵처럼 새 글을 가리키는 파일만 git add합니다. 나머지 과거 페이지는 이번 커밋에 넣지 않습니다. 커밋 전에는 git diff --cached --name-only로 실제로 올라갈 목록을 한 번 더 읽습니다.

5단계: 보안 훅 경고는 우회하지 않습니다. 생성된 HTML에는 오래전 예시 설정 문자열이 남아 있어 비밀값 검사 훅이 반복해서 걸릴 수 있습니다. 이때 훅을 끄는 대신, 경고된 정확한 문자열이 든 경로만 골라 스테이징에서 빼고, 새 글 파일이 여전히 스테이징되어 있는지 확인한 뒤 커밋합니다. 무인 실행에서 검사 자체를 끄는 것은 가장 나쁜 선택입니다.

6단계: 게시 후에는 주소를 직접 확인합니다. 푸시가 성공해도 GitHub Pages 배포는 몇 분 뒤에야 끝날 수 있습니다. Pages 상태가 built이 된 뒤 새 글 주소가 HTTP 200으로 응답하고, 제목이 기대한 값과 같은지 확인해야 완료로 봅니다. 푸시 성공 메시지만으로는 게시가 끝났다고 말할 수 없습니다.

정리하면, 배포 자동화의 안정성은 글을 쓰는 실력보다 무엇을 커밋하지 않을지를 정해 두는 데서 나옵니다. 저장소 상태가 지저분할수록 범위를 좁히고, 검사를 우회하지 말고, 마지막에는 실제 주소로 확인하는 순서를 지키는 것이 좋습니다.
