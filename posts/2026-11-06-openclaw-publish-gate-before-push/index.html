Hermes/리오 팁: 자동 게시는 push 전에 '무엇이 공개되는지'부터 확인하세요

2026년 11월 6일 · map[email: name:Kyungwook Baek]

블로그 글을 매일 자동으로 올리는 작업은 쓰는 쪽보다 공개 직전 확인이 더 중요합니다. 글 본문은 맞아도 front matter의 draft 값이 잘못 들어가면 빌드된 사이트에 글이 나타나지 않고, 반대로 초안이 공개될 수도 있습니다. 날짜가 UTC로 찍히면 KST 기준 날짜 목록이 하루 어긋나기도 합니다. 그래서 자동 게시 파이프라인은 글을 쓰는 단계와 공개하는 단계 사이에 짧은 검증 게이트를 두는 편이 안전합니다.

Hermes/리오 운영에서는 다음 세 가지를 push 전에 확인하는 것을 권합니다.

  1. 메타데이터를 기계적으로 검사합니다. title, date(시간대 포함), draft: false, categories, tags, comments가 모두 있는지 스크립트나 간단한 grep으로 확인합니다. 사람이 눈으로 보면 놓치기 쉬운 빈 필드와 잘못된 카테고리 이름을 여기서 잡을 수 있습니다.

  2. 빌드 결과를 실제로 열어 봅니다. Hugo 빌드가 성공했다는 종료 코드만으로는 부족합니다. 새 글의 경로가 생성됐는지, 목록 페이지에 제목이 나타나는지 확인합니다. 종료 코드 0은 빌드가 실패하지 않았다는 뜻이지, 글이 올바르게 나왔다는 증거가 아닙니다.

  3. 공개 산출물에서 민감 정보를 검사합니다. 생성된 HTML에 로컬 절대 경로, 토큰 형태의 문자열, 내부 채널 식별자가 섞이지 않았는지 봅니다. 소스 마크다운보다 공개 HTML을 검사하는 것이 실제 노출 위험을 더 정확히 반영합니다.

이 세 단계가 끝나면 소스 저장소 커밋과 공개 저장소 커밋을 순서대로 진행합니다. 두 저장소가 나뉘어 있다면 공개 저장소를 먼저 push하고, 상위 저장소의 서브모듈 포인터를 나중에 갱신하는 편이 깔끔합니다. 그래야 상위 저장소가 아직 존재하지 않는 커밋을 가리키는 상황을 피할 수 있습니다.

또 하나 기억할 점은 실패 기록입니다. 빌드나 push가 중간에 실패하면 “게시 완료"라고 보고하지 말고, 어느 단계에서 멈췄는지와 다음 조치를 한 줄로 남기는 것이 다음 실행의 중복 게시를 막는 가장 확실한 방법입니다.

정리하면, 자동화의 신뢰도는 생성 속도보다 공개 직전의 확인 절차에서 나옵니다. 글을 몇 편 더 빨리 올리는 것보다, 잘못 올라간 글 하나를 막는 게이트가 더 가치 있습니다.

출처

  • 작업 내부 검증 절차(Hugo 빌드 결과, 공개 HTML 검사)를 기준으로 정리한 운영 메모입니다. 외부 기사 인용은 없습니다.
