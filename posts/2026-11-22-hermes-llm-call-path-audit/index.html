Hermes/리오 팁: 외부 모델을 부르는 크론은 보존 설정을 '실측'으로 확인한다

2026년 11월 22일 · map[email: name:Kyungwook Baek]

도입: 설정이 맞는지는 호출 결과로 확인해야 한다#

자동화 작업이 외부 모델을 부를 때 점검표의 첫 줄은 보통 “보존 설정 켜짐"입니다. 설정 화면을 확인하고 체크 표시를 하면 끝나는 것처럼 보입니다. 하지만 오늘 나온 라우터 사례처럼, 같은 설정이 있어도 실제 요청이 지나가는 경로는 바뀔 수 있습니다. 그래서 Hermes/리오의 크론 작업에서는 설정 이름이 아니라 호출 결과로 확인하는 쪽을 기본값으로 둡니다.

1. 데이터를 먼저 세 단계로 나눈다#

모든 크론 작업이 같은 보호 수준을 요구하지는 않습니다. 작업 시작 전에 입력 데이터를 세 단계로 나눠 두면 이후 판단이 쉬워집니다.

  • 공개 데이터: 공개 뉴스, 공개 문서 요약. 일반 엔드포인트 사용을 허용합니다.
  • 내부 데이터: 사내 보고서 초안, 내부 지표. 허용 제공사 목록과 계약 조건을 확인한 경로만 씁니다.
  • 민감 데이터: 개인정보, 계정 정보, 고객 원본. 외부 호출을 하지 않거나, ZDR로 검증된 엔드포인트로만 보냅니다.

분류 결과는 작업 설정 파일에 한 줄로 남깁니다. 나중에 작업 목록을 훑을 때 어떤 작업이 어떤 경로를 쓰는지 바로 보입니다.

2. 경로를 로그에 남긴다#

호출이 끝난 뒤에는 응답 메타데이터에서 어떤 제공사와 엔드포인트가 처리했는지 기록합니다. 제공사 정보가 응답에 없다면 라우터의 요청 로그나 사용 내역에서 같은 값을 찾을 수 있는지 먼저 확인합니다. 기록이 없는 호출은 “확인되지 않은 호출"로 분류하고, 민감 데이터 작업이라면 실행을 멈추는 쪽이 안전합니다.

3. 주기적으로 카나리 문장을 보낸다#

이번 사례에서 중요한 것은 외부 테스트가 실제 경로를 드러냈다는 점입니다. 내부에서도 같은 방식을 흉내 낼 수 있습니다. 공개 데이터로만 구성된 무해한 문장을 일주일에 한 번 같은 라우터로 보내고, 응답에 기록된 제공사와 엔드포인트를 허용 목록과 대조합니다. 문장 안에는 실제 고객 정보나 계정 정보를 넣지 않습니다. 목적은 경로가 바뀌었는지를 보는 것이고, 내용을 평가하는 것이 아닙니다.

4. 허용 목록은 날짜를 붙여 관리한다#

허용 목록에 “2026-11-22 확인"처럼 확인 날짜를 붙이면 오래된 목록을 그대로 믿는 실수를 줄일 수 있습니다. 제공사 공지나 라우터 변경 공지가 올라오면 목록을 즉시 다시 확인하고, 변경 전후 결과를 짧게 기록합니다. 이 과정은 사람이 최종 승인하는 항목으로 두는 것이 좋습니다.

5. 실패 시 대체 경로를 미리 정한다#

검증이 실패했을 때 작업을 그냥 재시도하면 같은 문제가 반복됩니다. 다음 세 가지 중 하나를 미리 정해 둡니다.

  1. 로컬 모델이나 사내 엔드포인트로 낮은 품질의 대체 실행을 한다.
  2. 민감도가 높은 작업이라면 실행을 중단하고 사람에게 보고한다.
  3. 공개 데이터 작업이라면 이전 캐시 결과를 쓰고 “검증 전” 표시를 붙인다.

점검 체크리스트#

  • 작업별 데이터 분류가 설정 파일에 적혀 있는가
  • 응답 또는 라우터 로그에서 실제 처리 경로를 확인했는가
  • 주간 카나리 호출 결과가 허용 목록과 일치하는가
  • 허용 목록에 확인 날짜가 있는가
  • 검증 실패 시 대체 경로가 정해져 있는가

설정은 한 번 맞추는 것이고, 경로는 계속 확인하는 것입니다. 이 차이를 크론 설계에 반영하면 “분명히 켜 놨는데” 하는 상황을 줄일 수 있습니다.
