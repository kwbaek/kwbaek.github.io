Hermes/리오 실전 팁: '팀워크' 패턴으로 읽는 장기 과제 위임(Delegate) 아키텍처 설계

2026년 9월 1일 · map[email: name:Kyungwook Baek]

오늘 AI/ML 트렌드에서 소개된 **Google Antigravity의 ‘Teamwork’**는 여러 에이전트가 서로의 결과물을 비평·재작업하며 수 시간~수일에 걸쳐 학술 난제를 해결한 사례입니다. 단일 모델 호출로는 도달하지 못했던 성과가 “협업하는 팀” 구조에서 나왔다는 점이, Hermes/리오 환경에서 delegate_task로 서브에이전트를 운용할 때도 그대로 적용되는 설계 원칙입니다.

1. 왜 “한 번에 다 시키기"는 장기 과제에서 실패하는가#

Hermes/리오에서 복잡한 리서치·코딩·데이터 정리 작업을 단일 프롬프트로 서브에이전트에 던지면 흔히 이런 문제가 생깁니다.

  • 컨텍스트가 길어질수록 초반 지시가 희석되어 후반 작업에서 원래 목표를 놓침
  • 중간 산출물을 검증하는 단계가 없어 오류가 누적된 채로 끝까지 진행
  • 서브에이전트가 막히면 부모가 결과를 받을 때까지 문제를 알 수 없음

Antigravity Teamwork의 핵심은 이 문제를 “단일 에이전트의 인내심"이 아니라 역할 분리 + 상호 비평 루프로 풀었다는 점입니다.

2. Hermes/리오에서 적용 가능한 역할 분리 패턴#

delegate_task의 tasks 배열(병렬 배치)과 role: orchestrator를 조합하면 아래와 같은 3단계 구조를 만들 수 있습니다.

[1단계: 탐색 에이전트 (Explorer)]
  - 목표: 문제 공간을 넓게 스캔, 후보안 3~5개 생성
  - 산출물: 후보안 + 각각의 리스크/근거

        │  (부모가 후보안을 취합·1차 필터링)
        ▼

[2단계: 실행 에이전트 (Executor, 병렬)]
  - 목표: 필터링된 후보안 각각을 실제로 구현/검증
  - 산출물: 실행 결과 + 실제 실행 로그 (주장이 아니라 증거)

        │  (부모 또는 별도 비평 에이전트가 결과를 대조)
        ▼

[3단계: 비평/통합 에이전트 (Reviewer)]
  - 목표: 실행 결과 간 모순 확인, 최종안 채택 근거 명시
  - 산출물: 채택/기각 사유가 포함된 최종 보고

이 구조에서 중요한 것은 각 단계 사이에 “검증 가능한 증거"가 오간다는 점입니다. Antigravity 사례에서도 “40페이지 증명이 Lean으로 검증됐다"는 식으로 결과가 재검증 가능한 형태였기에 신뢰할 수 있었습니다. Hermes/리오에서도 서브에이전트의 “완료했습니다” 보고를 그대로 믿지 말고, 실제 실행 로그·파일 경로·테스트 통과 여부 같은 검증 가능한 핸들을 요구하는 것이 이 패턴의 핵심입니다.

3. 실무 체크리스트#

  1. 탐색과 실행을 분리: 첫 위임에서 바로 “구현해줘"라고 하지 말고, 먼저 후보안을 넓게 받아본 뒤 좁혀서 실행을 맡긴다.
  2. 병렬 실행 에이전트에는 겹치지 않는 검증 기준을 준다: 같은 작업을 서로 다른 방식으로 검증하게 하면 상호 비평 효과가 생긴다.
  3. 증거 없는 완료 보고는 재검증: 특히 외부 부작용(파일 생성, 배포, 전송)이 있는 작업은 부모가 직접 결과물을 확인한 뒤에만 최종 완료 처리한다.
  4. 스티어링(steer)을 적극 활용: 서브에이전트가 라이브 트랜스크립트에서 궤도를 이탈하는 게 보이면 끝까지 기다리지 말고 즉시 방향을 재지정한다.

장시간 자율 작업일수록 “얼마나 똑똑한 모델을 쓰느냐"보다 “역할을 어떻게 쪼개고, 결과를 어떻게 검증하느냐"가 성패를 가릅니다. 오늘 Antigravity Teamwork 사례가 보여준 것도 결국 이 구조적 설계의 힘이었습니다.
