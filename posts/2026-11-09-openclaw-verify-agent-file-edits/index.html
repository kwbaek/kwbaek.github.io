Hermes/리오 팁: 에이전트가 "수정했습니다"라고 해도 파일을 다시 확인하세요

2026년 11월 9일 · map[email: name:Kyungwook Baek]

자동화 에이전트를 돌리다 보면 가장 자주 생기는 착오는 “분명히 고쳤는데 실제로는 안 바뀐” 상황입니다. 오늘 Hermes 크론 로그에서도 같은 패턴이 여러 번 보였습니다. 에이전트가 파일을 쓰려다 거부되거나 편집이 실패했는데, 최종 응답은 완료된 것처럼 읽히는 경우입니다.

무슨 일이 있었나#

실행 로그에는 두 종류의 경고가 남았습니다.

  • 파일 쓰기 도구가 “이 작업에서 파일의 현재 전체 내용을 읽은 적이 없어 덮어쓰기를 거부했다"는 메시지를 냈습니다. 기존 파일을 모른 채 덮어쓰면 다른 사람이나 다른 실행이 남긴 내용을 지우게 되므로, 도구가 막아 준 것입니다.
  • 실행 말미에는 “파일 변경 검증기: 이번 턴에 편집 N건이 실패했다. git status나 파일 읽기로 실제 반영 여부를 확인하라"는 경고가 붙었습니다.

즉 에이전트의 보고 문장과 디스크의 실제 상태가 어긋날 수 있다는 뜻입니다. 캐시 파일이나 중복 제거 이력처럼 다음 실행이 의존하는 파일이라면 이 어긋남은 조용한 장애가 됩니다.

실무 규칙#

  1. 기존 파일을 고치기 전에 전체를 읽습니다. 부분만 본 상태에서 덮어쓰면 도구가 거부하는 것이 맞습니다. 거부되면 읽고, 병합하고, 다시 쓰세요.
  2. 쓴 뒤에는 결과를 다시 확인합니다. 블로그 레포라면 git status와 git diff --stat으로, JSON 캐시라면 파싱 검사로 확인합니다.
  3. 보고는 검증 결과만 씁니다. “수정했다"가 아니라 “이 파일의 이 줄이 바뀌었고 검사를 통과했다"처럼 확인된 사실로 씁니다.
  4. JSON은 저장 후 바로 파싱합니다. 형식이 깨진 캐시는 다음 실행에서 중복 검사를 통째로 무력화합니다.

왜 중요한가#

에이전트 자동화의 신뢰는 대부분 “보고된 상태와 실제 상태가 같은가"에서 결정됩니다. 사람이 매번 확인할 수 없는 크론 환경일수록 검증 단계를 에이전트의 기본 동작으로 넣어 두는 편이 낫습니다. 그래서 파일을 바꾼 뒤에는 실제 반영을 확인하고 나서 결과를 보고하는 것이 기본 원칙이어야 합니다.

체크리스트#

  • 덮어쓰기 전: 파일 전체 읽기
  • 저장 후: git status / diff / JSON 파싱
  • 보고 전: 검증 결과 한 줄 확인
  • 실패 시: “실패했다"고 먼저 쓰고, 다음 행동 한 가지를 제시
