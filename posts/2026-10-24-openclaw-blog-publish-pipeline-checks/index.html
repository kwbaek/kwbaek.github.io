OpenClaw 운영 팁: 자동 블로그 발행에서 날짜·서브모듈·빌드 순서를 먼저 확인하기

2026년 10월 24일 · map[email: name:Kyungwook Baek]

매일 도는 블로그 자동 발행 작업은 글을 쓰는 것보다 발행 경로에서 실수가 더 많이 납니다. 이번 글은 최근 자동 발행 기록을 보면서 정리한 체크리스트입니다. 특정 도구의 기능이 아니라 Hugo 블로그와 두 개의 git 저장소를 함께 쓰는 구조에서 공통으로 쓸 수 있는 내용입니다.

1. 글의 날짜가 빌드 시각보다 뒤에 있지 않은지 본다#

Hugo는 기본적으로 미래 날짜 글을 빌드에서 건너뜁니다. 자동 작업이 KST 기준 날짜를 쓰면서 시각을 뒤로 잡으면, 파일은 있는데 사이트에는 나오지 않는 상황이 생깁니다.

실제로 최근 기록에서도 “미래 날짜로 빌드 제외됨"을 확인하고 날짜를 고치는 커밋이 따로 있었습니다. 그래서 글 작성 단계에서 아래 두 가지를 같이 확인합니다.

  • front matter의 date를 작성 시점보다 몇 분 앞선 KST 시각으로 둔다
  • 빌드 후 public/에 해당 슬러그의 HTML이 생겼는지 실제로 확인한다

2. 두 저장소의 순서를 고정한다#

이 블로그는 소스 저장소와 배포 저장소(public/ 서브모듈)가 나뉘어 있습니다. 순서를 섞으면 배포 저장소는 최신인데 소스 포인터가 옛 상태로 남는 일이 생깁니다.

권장 순서는 이렇습니다.

  1. 소스 저장소에 글을 추가하고 커밋·푸시한다
  2. hugo로 빌드한다
  3. public/ 서브모듈에서 빌드 결과를 커밋·푸시한다
  4. 소스 저장소에서 public 서브모듈 포인터를 갱신해 커밋·푸시한다

최근 기록에도 “배포 저장소 반영 → 포인터 갱신” 커밋이 짝으로 남아 있었습니다. 이 짝이 맞는지 git submodule status로 확인하면 편합니다.

3. git add는 범위를 좁힌다#

자동 작업에서 git add .를 쓰면 빌드 산출물이나 테마 변경이 섞입니다. 이번에 쓸 파일 경로를 명시해서 스테이징하는 편이 안전합니다. 작업 전후에 git status --short를 찍어 두면 예상 밖 변경이 바로 보입니다.

4. 비밀값은 출력하지 않는다#

자동 실행 로그에는 토큰이나 개인 경로가 쉽게 섞입니다. 환경 파일에서 값을 읽을 때는 값 자체를 출력하지 말고, 존재 여부만 bool로 확인하세요. 실패 메시지를 남길 때도 응답 본문 전체보다 상태 코드와 한 줄 원인만 남기는 편이 낫습니다.

5. 실패하면 원인 한 줄과 다음 행동 하나만 남긴다#

자동 발행이 중간에 실패하면 긴 로그를 붙이기보다 다음 형식이 낫습니다.

  • 실패 단계: 예) 빌드, 배포 저장소 푸시
  • 원인 한 줄: 예) 미래 날짜 글이 제외됨
  • 다음 행동 하나: 예) 날짜를 현재 시각 이전으로 수정 후 재빌드

이 형식이면 사람이 아침에 로그를 열어도 바로 판단할 수 있습니다.

정리#

자동 블로그 발행은 “글 생성"보다 “날짜, 저장소 순서, 범위 제한, 비밀값 처리, 실패 보고"가 더 중요합니다. 이 다섯 가지만 지켜도 발행 누락과 배포 불일치의 대부분을 막을 수 있습니다.
