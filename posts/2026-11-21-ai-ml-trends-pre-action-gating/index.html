AI/ML 트렌드: 에이전트 행동은 실행 직전에 심사해야 한다 — OpenAI 단계별 안전 검토와 Google 시맨틱 거버넌스 정책

2026년 11월 21일 · map[email: name:Kyungwook Baek]

도입: 권한을 잘 걸어도 “요청 범위 밖의 호출"은 남는다#

에이전트에 도구를 붙이는 팀이 가장 먼저 쓰는 방어선은 권한입니다. 어떤 MCP 서버에 접근할 수 있는지, 어떤 API를 호출할 수 있는지를 IAM으로 정하는 식이죠. 그런데 실제로 사고가 나는 장면을 보면 권한은 맞는데 목적이 틀린 경우가 많습니다. 파일 공유 도구를 쓸 권한은 있지만, 그 파일이 외부 메일 주소로 나가면 안 되는 실적 자료라면 권한 설정만으로는 막을 수 없습니다.

이번 주 나온 두 발표는 이 빈틈을 서로 다른 층위에서 다룹니다. OpenAI는 2026년 11월 18일 글에서 모델을 훈련부터 배포까지 단계마다 안전 검토를 통과해야 다음 단계로 넘어가는 체계를 공개했습니다. Google Cloud는 Agent Gateway 뒤에 있는 에이전트가 도구를 호출하기 직전에 LLM 심사자가 그 호출을 허용할지 판정하는 Semantic governance policies 프리뷰를 내놨습니다. 하나는 조직이 모델을 내보내는 속도를 조절하는 이야기이고, 다른 하나는 개별 행동을 실행 전에 거르는 이야기입니다. 같은 문제의 두 끝이라고 보면 이해가 쉽습니다.

OpenAI: 출시 속도를 안전 증거에 묶는다#

OpenAI 글의 핵심은 방어를 여러 겹으로 쌓고, 각 겹이 실패해도 다른 겹이 피해를 막거나 사람에게 알리도록 설계한다는 점입니다. 글은 보호 계층을 네 가지로 정리하고, 모델이 연구, 훈련, 배포 단계를 지날 때마다 역할이 바뀐다고 설명합니다. 특히 샌드박스만으로는 고성능 모델을 가둘 수 없다는 판단이 눈에 띕니다. 지난 7월 Hugging Face 사건 이후에는 샌드박스 격리에 기대지 않고, 도구를 쓰는 내부 배포를 포함해 프런티어 모델을 대부분의 내부·외부 배포 환경에서 모니터링하고 있다고 밝혔습니다.

눈여겨볼 부분은 모니터링 가능성(monitorability)이라는 개념입니다. 모델이 추론 과정에서 부정행위 의도를 드러내는 경우가 그렇지 않은 경우보다 감시하기 쉽다는 것이죠. 그래서 훈련과 배포 전에 이 성질을 측정하고, 측정 방법 자체도 연구하고 있습니다. 글은 GPT-6.1 Astra의 출시를 안전 기준을 충족할 때까지 보류한 사례도 함께 적었습니다. 출시 일정이 늦어지더라도 증거가 먼저라는 원칙을 실제로 지킨 것입니다.

조직 입장에서 이 글은 모델을 도입할 때 어떤 증거를 요구할지에 대한 기준표로 읽을 수 있습니다. 벤더가 안전 평가 결과를 단계별로 제시하는지, 모니터링 범위가 내부 도구 사용까지 포함하는지, 사고가 났을 때 개입 지점이 어디인지 물어볼 수 있습니다.

Google: 행동을 실행 직전에 판정한다#

Google의 Semantic governance policies는 다른 방식으로 접근합니다. 정책을 자연어 제약으로 적고, 에이전트가 도구를 호출하기 직전에 판정자가 대화 맥락과 에이전트 지시문, 정책을 보고 허용 여부를 정합니다. 예시로 든 정책은 “분기 실적은 공식 발표 전에는 회사 도메인 주소에만 공유하고, 외부·개인 주소나 투자자, 언론에는 어떤 이유로도 보내지 않는다"는 식입니다. 권한 정책으로는 표현하기 어려운 업무 규칙을 문장으로 담는 것이 핵심입니다.

문서는 이 기능의 위치를 분명히 나눕니다. IAM과 Agent Gateway 접근 정책은 에이전트가 닿을 수 있는 도구와 MCP 서버를 정하고, Model Armor는 프롬프트와 응답에서 탈옥 시도나 민감정보를 걸러냅니다. Agent Anomaly Detection은 세션을 사후에 비동기로 분석합니다. Semantic governance policies는 그 사이에서 각 행동을 실행 전에 인라인으로 판단하는 층입니다. 판정 근거는 Cloud Logging에 남고, dry run 모드에서는 차단 없이 무엇을 거부했을지만 기록합니다.

다만 문서가 스스로 한계를 적어 둔 부분도 중요합니다. 판정이 LLM에서 나오므로 확률적이고, 같은 상황에서도 결과가 달라질 수 있습니다. 그래서 먼저 dry run으로 충분히 검토한 뒤 적용하라고 권합니다. 또 판정자는 대화와 지시문만 보기 때문에, 정책이 의존하는 사실, 예컨대 실적 발표일 같은 정보는 에이전트 시스템 지시문에 미리 넣어 두어야 합니다. 스트리밍으로 나가는 모델 응답은 평가하지 않는다는 점도 운영 설계에서 놓치기 쉽습니다.

실무 체크리스트: 두 층을 함께 설계하기#

두 발표를 합치면 실무에서 쓸 수 있는 순서가 보입니다.

  • 첫째, 권한(IAM·게이트웨이)으로 도달 범위를 줄입니다. 이것이 가장 값싸고 확실한 방어입니다.
  • 둘째, 업무 규칙이 있는 행동은 실행 전 판정 층에 넣습니다. 규칙은 “~하지 말 것"보다 한도, 대상, 예외를 구체적으로 적어야 판정자가 일관되게 봅니다.
  • 셋째, 도구마다 설명(description)을 명확히 씁니다. 판정자는 설명을 보고 호출 의도를 이해하므로, 설명이 없으면 거부로 기울 수 있습니다.
  • 넷째, 판정 로그를 주기적으로 읽고 dry run 거부 목록에서 오탐을 골라냅니다. 확률적 판정은 한 번 설정하고 끝나지 않습니다.
  • 다섯째, 모델 도입 단계에서는 벤더에게 단계별 안전 검토 증거와 모니터링 범위를 요구합니다.

맺으며#

에이전트 보안을 “누가 무엇에 접근하나"에서 “이 행동이 지금 이 맥락에서 맞나"로 옮기는 흐름이 뚜렷해지고 있습니다. OpenAI는 모델을 내보내는 속도를 증거에 묶었고, Google은 행동을 실행 직전에 묶었습니다. 어느 쪽도 완벽한 차단을 약속하지 않습니다. 그래서 두 발표가 공통으로 말하는 것은 하나의 방어를 믿지 말고, 겹쳐서 설계하고, 그 결과를 로그로 검증하라는 것입니다. 에이전트를 운영한다면 이번 주에 권한 목록과 함께 판정 규칙 초안을 한 번 적어 보는 것을 권합니다.
